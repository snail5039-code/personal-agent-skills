# AI 프로젝트 서술·면접 근거 가이드

2026-10-27 사용자가 제공한 AI 엔지니어 현직자 대화의 조언을 자소서 작성 기준으로 재구성했다. 한 회사와 한 실무자의 관점이므로 채용 시장 전체의 규칙이나 지원 회사의 사실로 단정하지 않는다. 자동 전사가 불명확한 고유명사·수치·회사 내부 사례는 옮기지 않았다.

## 공고와 프로젝트를 연결할 때

- 공고가 AI를 **내부 업무 자동화**, **기존 서비스 개선**, **새 제품·콘텐츠 개발**, **데이터·도구 연결** 중 어디에 쓰려는지 공식 자료로 파악한다. 같은 RAG·에이전트 경험도 이 목적에 맞는 문제와 기여를 골라 설명한다.
- “에이전트를 만들었다”에서 멈추지 않는다. 누가 어떤 업무를 수행하며 어디서 막혔는지, 이를 인터뷰·관찰·사용 기록 등 무엇으로 확인했는지 적는다. 실제 사용자를 조사하지 않았다면 조사했다고 쓰지 않는다.
- 요구를 구체화할 때 데이터 출처·접근 권한·허용되지 않는 오류·사람의 승인·응답 시간·비용처럼 결과를 바꾸는 제약을 확인한다. 해당 프로젝트에서 실제로 다룬 제약만 본문에 넣는다.

## 기술 선택과 검증의 증거

- RAG, 긴 컨텍스트, 정형 DB 조회, 검색 도구·MCP 연결 등 가능한 접근 중 무엇을 왜 선택했는지 설명한다. 기술명이나 프레임워크 사용 사실만으로 전문성을 주장하지 않는다.
- 잘된 예시뿐 아니라 실패 질문이나 예외 상황을 어떻게 찾아냈는지 확인한다. 평가셋·테스트 시나리오의 작성 기준, 변경 전후 결과, 남은 한계를 제시한다. 숫자가 없다면 실제 오류, 사용자 피드백, 재현·수정 기록으로 설명한다.
- 사용자에게 제공한 서비스라면 사용 여부와 피드백을 반영한 변경을 확인한다. 운영·사용 실적이 없으면 시험 결과를 실제 사용자 성과로 바꾸어 쓰지 않는다.
- 필요할 때 응답 지연, 토큰·API 비용, 검색 품질, 권한과 위험한 도구 실행을 함께 다룬다. 평가 없이 “잘 작동했다”고만 쓰지 않는다.
- 프롬프트, 도구 호출, 검색 결과가 최종 모델 입력과 답변에 어떻게 이어지는지 직접 확인한 경험이 있다면 이를 구체적으로 쓴다. 직접 확인하지 않은 내부 동작은 추측해서 설명하지 않는다.

## AI 도움을 받아 개발한 경험

- AI 도구 사용 자체를 숨기거나 직접 타이핑한 것처럼 꾸밀 필요는 없다. 지원자가 정의한 문제, 선택한 구조, 생성 결과 검토, 테스트, 수정, 최종 책임을 각각 실제 범위대로 쓴다.
- 이력서·자소서에 적은 기술은 면접에서 “왜 썼는가, 무엇이 실패했는가, 다른 방법은 무엇인가, 어떻게 검증했는가”에 답할 수 있어야 한다. 피상적으로 실행만 해 본 기술은 핵심 역량으로 부풀리지 않는다.
- 팀 프로젝트에서는 본인의 결정과 구현·통합·검증 범위, 팀원과 합의한 인터페이스 및 다른 사람의 기여를 구분한다.

## 초안 점검 질문

1. 첫 문장에 실제 문제 또는 문항의 답이 보이는가?
2. 지원자의 이름을 지워도 다른 팀원이 똑같이 쓸 수 있는 문장만 남지 않는가?
3. 기술을 고른 이유와 대안·제약을 설명할 수 있는가?
4. 실패 사례, 평가 방법, 수정 결과를 근거로 보여줄 수 있는가?
5. 사용자 피드백·운영 성과와 로컬 테스트를 정확히 구분했는가?
6. AI가 만든 결과 중 지원자가 직접 검수하고 책임진 범위가 명확한가?

본문에는 문항에 맞는 근거만 선택한다. 이 목록을 모두 채우려고 확인되지 않은 과정이나 성과를 만들지 않는다.
