# 결정 근거와 튜닝

템플릿 기본값은 rag_agent_practice(한국어 PDF 59개·1,258쪽, 금융·공공·커머스·법률·의료, 골든셋 309문제)에서 실험으로 정했다. 새 문서에서도 출발점으로 쓰고, 평가 결과가 다르면 아래 조치표로 바꾼다.

## 추출

| 결정 | 근거 |
|---|---|
| 여백 위 6%·아래 7%·좌우 3% 버림 | 쪽번호가 높이 93.8~96.6%에 있었다. 머리말·꼬리말·쪽번호가 청크에 섞이면 검색 잡음 |
| 1행/1열 표는 본문으로 | 안내 박스가 표로 잡힌 경우가 299개 |
| 셀 글자가 영역 글자의 70% 미만인 표는 본문으로 | 칸 안의 긴 글을 빈칸으로 읽어 내용이 통째로 사라지는 표 17개 |
| 2단 감지 후 왼쪽 단 → 오른쪽 단 | 논문 172쪽이 2단. 그대로 읽으면 두 단 문장이 섞인다 |
| 글자 없는 쪽은 쪽 전체를 이미지 대상으로 | 벡터 곡선으로 그린 글자 53쪽, (cid) 깨짐 46쪽, 이미지 조각 25쪽 |
| OCR은 RapidOCR PP-OCRv5 한국어, 방향 분류기 끔 | CPU로 충분. 분류기가 정방향 문단을 뒤집어 글자가 깨졌다 |
| 이미지 속 표는 레이아웃 모델 + SLANet+로 행·열 복원 | 56개 표 복원. 1행/1열·빈칸 50% 초과는 실패로 보고 OCR 글자로 |
| 차트·도식은 Vision 모델(gemini-3.6-flash)로 표·화살표 마크다운 | 차트 277·도식 152개. 값은 표, 어림값은 (추정), 마지막에 요약 |

## 청킹

| 청킹 | 검색 MRR (309문제) | 에이전트 정답률 (200문제, 2회) | 평균 검색 |
|---|---|---|---|
| 300/50 | **0.830** | 0.786 / 0.796 | 1.77회 |
| **500/60 (기본)** | 0.819 | **0.827 / 0.811** | **1.60회** |
| 800/100 | 0.812 | 0.806 | 1.54회 |

- 검색 지표가 가장 좋은 설정과 에이전트 정답률이 가장 좋은 설정이 다를 수 있다 → 최종 선택은 에이전트 평가로
- 표 질문 정답률(0.55~0.61)은 청킹으로 해결되지 않았다 → 검색 방식 문제였다
- 표는 행 단위로 자르고 헤더를 반복해야 행 하나만 검색돼도 열 의미가 남는다
- 2단 논문은 문단 단위로 (길이로 자르면 문단 중간이 잘린다)

## 검색

| 설정 (500/60, 200문제) | 정답률 | 근거 쪽 적중 | 잘못된 보류 | 표 정답률 |
|---|---|---|---|---|
| 처음: 표=MMR, 분야 필터만 | 0.827 / 0.811 | 0.781 | 0.112 | 0.576 |
| + 앞뒤 청크 1개 | 0.806 | 0.760 | 0.128 | 0.545 |
| + 표도 Hybrid | 0.842 | 0.770 | 0.107 | 0.667 |
| **+ 분야 결과에 전체 결과 섞기 (기본)** | **0.872 / 0.898** | **0.832** | **0.066** | **0.667 / 0.758** |

- Hybrid(벡터 + Kiwi BM25, RRF): 개념 질문은 벡터, 숫자·사건번호·고유명사는 BM25가 잘 찾는다
- MMR은 같은 표의 행 청크를 하나만 가져와 표 질문에 불리했다
- 에이전트가 분야를 잘못 고르면 정답률이 0.25~0.33 → 분야 결과만 쓰지 않고 전체 결과와 섞는다
- RAGAS 분석: 실패 34개 중 24개가 "정답 쪽은 찾았지만 답이 적힌 청크는 못 찾음" → 앞뒤 청크 붙이기

## 에이전트

- 단일 에이전트 + search 툴 하나. 기능이 검색뿐이라 슈퍼바이저는 두지 않았다
- 검색 최초 포함 최대 3회 (`ToolCallLimitMiddleware`로 강제), 근거 없으면 보류
- 구조화 출력에서 `judgement`(근거 판단)를 `status`보다 먼저 쓰게 한다
- 프롬프트 p2 규칙(질문 부분마다 근거 확인, 표 수치로 계산 가능하면 답함, 연도·대상·단위 일치)으로 표 정답률 0.667/0.758 → 0.818/0.818, 답변 불가 보류 100% 유지
- 모델: gemini-3.5-flash-lite가 3.6-flash·2.5-flash 등보다 빠르고(질문당 약 4초) 재검색·보류도 제대로 함. 채점 모델은 실험끼리 고정

| | 에이전트 | 기본 RAG (1회 검색) |
|---|---|---|
| 정답률 (2회) | **0.888 / 0.903** | 0.867 / 0.842 |
| 잘못된 보류 | **13 / 12** | 18 / 19 |
| 평균 시간 | 4.1초 | **2.4초** |

에이전트도 76%는 검색 1번으로 끝냈다 → 재검색은 어려운 문제에서만 쓰인다.

## 증상별 조치표

`evaluate agent`의 report.md 실패 사례 분류로 진단한다.

| 증상 | 확인 | 조치 |
|---|---|---|
| 오답인데 검색도 정답 쪽을 못 찾음 | `evaluate retrieval`의 놓친 문제, 정답 쪽 청크 미리보기 | 추출부터 확인(표·OCR 누락?) → 청크 크기 비교(300/50·800/100) → `FETCH_K`·`TOP_K` ↑ → 리랭커 |
| 검색은 정답 쪽을 찾았는데 오답 | 답이 적힌 청크가 결과에 있었나 | `NEIGHBORS` 2, 프롬프트 규칙(부분별 근거·연도/단위 일치) 추가 후 `PROMPT_VERSION` ↑ |
| 잘못된 보류가 많음 | judgement에 "근거 없음" 이유 | 대부분 검색 문제(위 두 줄). 표 계산으로 답할 수 있는데 보류하면 계산 허용 규칙 |
| 답변 불가 문제에 답함 | answer와 citations | "근거가 없으면 보류" 규칙 강조, 더 강한 모델 비교 |
| 표 질문만 약함 | context_type=table 정답률 | 표 추출 미리보기(헤더·병합 칸), 행 단위 청킹 확인, MMR을 쓰고 있지 않은지 |
| 특정 분야만 약함 | 분야별 표, 검색 기록의 domain | 분야 폴더 구성, `domain_fallback` 켜져 있는지 |
| 너무 느림 | 평균 검색·시간 | 더 빠른 모델, `MAX_SEARCHES` 2, 기본 RAG와 정답률 차이 비교 |

한 번에 하나만 바꾸고, 결과 폴더 이름(설정·모델·프롬프트 버전)이 달라지게 해서 비교한다.
