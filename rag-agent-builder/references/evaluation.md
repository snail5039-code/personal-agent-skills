# 평가 가이드

## 골든셋 CSV 형식

`data/` 바로 아래에 UTF-8(BOM 가능) CSV로 둔다. 문서 폴더(`data/<분야>/`)에 넣지 않는다 (문서로 색인되면 안 된다).

| 열 | 필수 | 설명 |
|---|---|---|
| `id` | 권장 | 문제 id (없으면 q001…). 평가 이어서 실행·특정 문제만 풀기에 쓴다 |
| `question` | 필수 | 실제 사용자처럼 묻는 질문 |
| `target_answer` | 필수 | 정답 (LLM 채점 기준) |
| `target_file_name` | 필수 | 정답 문서 파일명 (확장자 있어도 없어도 됨). 여러 문서면 `A.pdf \|\| B.docx` |
| `target_page_no` | 선택 | 정답 위치 번호. PDF는 물리 쪽(1부터, 인쇄된 쪽번호 아님), 슬라이드·시트·섹션은 추출 미리보기의 번호. 여러 쪽 `3,4`, 여러 문서 `3 \|\| 10,11`. **비우면 파일만 맞으면 적중** |
| `answerable` | 선택 | `false`면 문서에 없는 질문 (보류해야 정답). 기본 true |
| `domain` | 선택 | 분야 (분야별 결과 표) |
| `context_type` | 선택 | `paragraph`·`table`·`image` 등 근거 유형 (유형별 결과 표) |
| `evidence` | 선택 | 근거 원문 구절 (검수용) |

사용자 골든셋의 열 이름이 다르면 이 형식으로 바꾼 사본을 만들어 쓴다.

## 좋은 골든셋

- 분야·근거 유형(문단/표/이미지·차트)을 섞는다. 처음엔 20~30문제로 빠르게, 비교 실험은 100문제 이상
- 질문은 정답이 맞다/틀리다로 판단되게 구체적으로 (연도·대상·단위 포함)
- 문서에 없는 질문 3~5개 (보류 확인용)
- 스캔·차트에 답이 있는 문제를 넣으면 OCR·Vision 단계가 실제로 도움이 되는지 확인된다
- 초안(`rag.make_golden`)은 반드시 사람이 검수한다: 질문이 너무 쉬운지(답이 질문에 드러남), 정답·쪽이 맞는지, 다른 문서와 헷갈리는지

## 지표

| 평가 | 지표 | 의미 |
|---|---|---|
| retrieval | hit@1/3/5, recall@5, MRR, ms | 정답 위치가 검색 상위에 있나 (LLM 비용 없음). 청킹·검색기 고르기 |
| agent | 정답률 | 답할 수 있는 문제 중 LLM 채점 정답 (보류는 오답) |
| | 근거 쪽 적중 | 답에 든 근거 위치가 정답 위치인가 |
| | 검색 적중 | 검색한 청크에 정답 위치가 있었나 → 오답이 검색 탓인지 답변 탓인지 구분 |
| | 잘못된 보류 / 답변 불가 보류 | 답할 수 있는데 보류한 비율 / 없는 질문을 보류한 비율 (높을수록 좋음) |
| | 평균 검색·시간 | 재검색 비용 |

- 채점 모델(`JUDGE_MODEL`)은 실험 내내 고정한다. 바꾸면 이전 결과와 비교할 수 없다
- 같은 설정도 1~2%p 흔들린다 → 차이가 작으면 `--tag run2`로 반복
- 기본 RAG(`--mode rag`)와 비교해 에이전트가 정답률을 얼마나 올리고 시간을 얼마나 쓰는지 보고한다

## 더 깊은 실패 분석 (선택)

practice에서는 아래 두 가지로 실패 원인을 나눴다. 필요할 때 `details.jsonl`을 입력으로 추가한다.
- RAGAS: context_recall(검색에 정답 내용이 있었나), faithfulness(답이 검색 내용에만 근거했나) → 검색 실패 / 판단 실패 / 지어냄 구분
- agentevals trajectory: 검색어가 매번 바뀌었는지, domain을 맞게 골랐는지 → 맞을 때와 틀릴 때 정답률 비교
