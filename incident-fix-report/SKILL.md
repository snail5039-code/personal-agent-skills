# 장애 조치 보고서

장애를 고치는 것과, 다음 사람이 같은 장애를 다시 파지 않게 하는 것은 다른 일이다. 이 스킬은 둘 다 한다.

보고서의 독자는 **이 장애를 처음 보는 사람**이다. 보통은 인수자이거나, 몇 달 뒤의 본인이다. 그 사람이 코드를 열지 않고도 "무슨 일이 있었고, 왜 그랬고, 뭘 했고, 뭐가 남았는지"를 알 수 있어야 한다.

## 작업 순서

| 단계 | 하는 일 |
|:---:|:---|
| 1 | **재현** · 실제 서비스에서 증상을 직접 확인한다 |
| 2 | **추적** · 코드와 로그로 원인을 좁힌다 |
| 3 | **수정** · 최소 범위로 고치고 회귀 테스트를 남긴다 |
| 4 | **검증** · 수정을 되돌리면 테스트가 실패하는지 확인한다 |
| 5 | **보고** · 과정을 HTML 보고서로 남긴다 |

## 1. 재현 — 증상을 직접 본다

- 보고받은 말이 아니라 **실제 입력과 실제 응답**을 확보한다. 재현하지 못한 증상은 추적하지 않는다.
- 재현되면 조건을 좁힌다. 세션을 새로 열면 되는가, 특정 계정만 그런가, 순서를 바꾸면 어떤가.
- 이 단계에서 "되는 것"도 함께 기록한다. **되는 것과 안 되는 것의 차이가 원인을 가장 빠르게 좁힌다.**

## 2. 추적 — 증상이 아니라 원인을 찾는다

- 로그에 실패 코드가 이미 남고 있는지 먼저 본다. 배포 없이 알 수 있는 것부터 확인한다.
- 외부 API가 얽히면 **인터페이스 정의서의 오류 코드 표**를 확인한다. 추측하지 않는다.
- 코드를 읽을 때는 호출 흐름을 따라간다. 어느 단계에서 갈라졌는지 짚을 수 있어야 한다.
- 가설이 틀리면 **틀렸다는 사실을 기록에 남긴다.** 증상과 맞아떨어졌던 가설일수록 반드시 남긴다. 지우면 다음 사람이 같은 길로 샌다.

원인은 세 가지로 갈라서 적는다. 조치 주체가 다르기 때문이다.

| 구분 | 누가 고치나 |
|:---|:---|
| 코드 결함 | 우리가 고친다 |
| 설정·환경 문제 | 값을 넣으면 해결된다. 코드 수정이 아니다 |
| 외부 시스템·연동 범위 | 우리가 못 고친다. 요청할 내용을 정리한다 |

## 3. 수정 — 최소 범위로

- 공용 테이블이나 공통 로직을 바꾸기 전에, **그 앞 단계에서 가로채는 방법**이 있는지 본다. 영향 범위가 훨씬 작다.
- 같은 문제를 이미 막아둔 코드가 어딘가 있는지 찾는다. 있으면 그 방식을 그대로 가져다 쓴다. 새로 설계하지 않는다.
- 고치면서 깨뜨린 호출처·테스트는 전부 함께 고친다.
- 사용자에게 보이는 문구가 **따라 해도 해결되지 않는 방법**을 안내하고 있다면 그것도 결함이다. 실제 해법으로 바꾼다.

## 4. 검증 — 테스트가 증상을 잡는지 본다

- 회귀 테스트를 추가한 뒤, **수정을 임시로 되돌려 그 테스트만 실패하는지** 확인한다. 이걸 안 하면 테스트가 무엇을 지키는지 모른다.
- 영향 범위를 덮는 스위트를 돌린다. 전체 스위트가 다른 이유로 안 돌면, 그 사실을 보고서에 적고 돌린 범위를 밝힌다.
- 로컬 테스트가 외부 서버로 실제 요청을 보내지 않는지 확인한다. 키가 없어 구조적으로 불가능한지, mock으로 막혀 있는지 확인하고 보고서에 적는다.

## 5. 보고서 작성

`template/report.html`을 복사해 내용을 채운다. 저장 위치는 저장소의 기존 문서 관례를 따른다(예: `docs/`).

### 구성

| 섹션 | 내용 |
|:---|:---|
| 요약 | 숫자 몇 개, 장애별 한 줄, **가장 중요한 한 줄** |
| 점검 결과 | 무엇을 어떤 입력으로 확인했고 결과가 어땠는지 표 |
| 장애별 | 증상 → 추적 → 원인 → 수정 → 검증 |
| 배포 | 브랜치, 태그, 되돌릴 태그, 변경 파일, 테스트 범위 |
| 남은 일 | 다음 사람이 바로 집을 수 있는 단위로 |

### 지켜야 할 규칙

**증상은 실제 그대로 넣는다.** 주고받은 대화, 로그 줄, 오류 문구를 다듬지 말고 그대로 싣는다. 요약하면 다음 사람이 같은 증상을 못 알아본다.

**틀린 가설을 남긴다.** "이렇게 의심했으나 아니었다"를 추적 단계에 배지와 함께 남긴다. 어떤 근거로 그렇게 의심했는지까지 적는다.

**확인한 것과 못 한 것을 가른다.** 섞어 쓰면 전부 확인한 것처럼 읽힌다. 못 한 것은 왜 못 했는지도 적는다.

**이름은 나오는 자리에서 푼다.** 변수·함수·코드값은 **처음 등장하는 자리 바로 아래**에 짧게 설명한다. 문서 끝에 용어집을 따로 두지 않는다. 읽다가 아래로 뛰어야 하면 안 읽는다.

**왜 다른 방법으로는 안 되는지 적는다.** 더 자연스러워 보이는 수정 방법이 있는데 그걸 택하지 않았다면, 이유를 적는다. 안 적으면 다음 사람이 "이렇게 하면 될 텐데"라며 되돌린다.

**단계 번호는 순서가 의미를 가질 때만 쓴다.** 추적 과정과 절차는 순서가 정보다. 그냥 나열하는 항목에는 번호를 붙이지 않는다.

**혼동하기 쉬운 지점에 경고를 단다.** 보고 과정에서 와전되기 쉬운 사실(예: "키가 없다"와 "기능이 없다")은 따로 박스로 뺀다.

**비밀번호·API 키·서버 접속 정보는 적지 않는다.** 환경변수 **이름**까지만 쓴다.

### 쓰지 말 것

- 재현하지 않은 증상을 원인과 함께 단정하기
- "수정했습니다"만 쓰고 무엇을 어떻게 검증했는지 빼기
- 확인 못 한 항목을 조용히 생략하기
- 코드 변경을 말로만 설명하기 — **before/after를 보여준다**
