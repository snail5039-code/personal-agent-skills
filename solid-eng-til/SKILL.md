# 솔리드 이엔지 학습 기록

현재 대화에서 공부한 내용과 사용자가 지정한 메모, 파일, 코드, 명령어를 바탕으로 작성한다. 사용자가 실제로 공부하거나 실행한 내용과 설명을 위해 새로 만든 예시를 구분한다. 학습 근거가 전혀 없으면 주제나 자료를 요청한다.

## 기록 위치

[리눅스 → 쿠버네티스 까지](https://app.notion.com/p/421c2c49a25080a98096cc715b1c122c?source=copy_link), 페이지 ID `421c2c49-a250-80a9-8096-cc715b1c122c`.

Notion 도구로 지정된 부모 페이지를 확인한 뒤, 학습 기록마다 그 아래에 하위 페이지를 하나 만든다. 제목은 `YYYY.MM.DD (짧은 학습 주제)` 형식으로 쓴다. 예시는 `2026.11.20 (쿠버네티스 Service)`다. 사용자가 학습 날짜를 알려주면 그 날짜를 쓰고, 생략하면 사용자 시간대의 오늘 날짜를 쓴다.

하위 페이지의 본문에는 아래 네 항목을 넣는다. 기존 기록을 다시 정리해 달라는 요청이면 지정된 부모 아래에서 날짜와 주제로 기존 하위 페이지를 찾아 본문을 고친다. 접근이나 쓰기에 실패하면 저장되지 않았음을 알린다. 저장 후에는 하위 페이지의 부모, 제목, 네 항목과 예시 코드 블록이 제대로 반영됐는지 확인하고 링크를 전달한다.

## 본문 양식

아래 제목과 순서를 그대로 사용한다. Notion 본문에서 네 항목은 `##`, 항목 안의 소주제는 `###`로 표시한다. 문단은 짧게 쓰고, 표는 옵션처럼 같은 기준으로 비교할 항목이 있을 때 사용한다. 코드는 언어를 지정한 별도 코드 블록에 둔다.

Notion의 실제 콜아웃 블록(`<callout icon="…" color="…">`)을 사용한다. 첫 항목의 시작에 파란색 🧭 **실습 순서** 카드를 넣어 읽는 순서를 보여 주고, 각 코드 블록 바로 아래에 초록색 ✅ **예상 결과** 카드를 둔다. 두 번째 항목에는 노란색 ⚠️ **실행 전 확인할 점** 카드로 주의점을 모은다. 콜아웃에는 바로 확인할 내용만 짧게 쓰고, 저장 후 Notion에서 콜아웃이 실제 블록으로 생성됐는지 확인한다.

### 1. 오늘 배운 내용

- 자료의 핵심 개념을 각각 소제목으로 나누고, 앞에서 배운 내용을 뒤에서 써먹는 순서로 배치한다. 처음 나오는 용어는 쉬운 말로 정의하고 무엇을 할 때 쓰는지 적는다. 함께 나오는 개념의 관계는 입력에서 결과까지의 흐름을 한 줄로 보여 준다. 예를 들어 `터미널에서 입력 → 셸이 해석 → 명령 실행 → 터미널에 결과 표시`처럼 쓴다.
- 핵심 명령어나 문법마다 짧은 예시를 붙인다. 성격이 다른 개념을 한 코드 블록에 몰아넣지 않는다. 기본 예시를 설명한 뒤, 여러 개념을 연결하는 응용 예시가 자연스러우면 이어서 보여 준다. 원본에 예시가 없으면 새로 작성하고 `학습용 예시`로 표시한다.
- 각 예시는 **무엇을 확인하는지 → 실행 위치와 필요한 입력 → 코드 → 예상 결과와 읽는 법** 순서로 설명한다. 파일을 쓰는 예시는 샘플 파일을 만드는 명령이나 파일 내용도 제공한다. 호스트와 VM처럼 실행 환경이 바뀌면 코드 블록을 나눈다. 출력이 환경에 따라 달라지면 실제 실행 결과처럼 단정하지 말고 무엇을 확인하면 되는지 적는다.
- 예상 결과 카드에 **터미널 출력 예시**를 별도의 `plain text` 코드 블록으로 넣는다. 입력 데이터에 맞는 출력 줄을 실행 순서대로 보여 준다. 실행 로그를 직접 확인했으면 관측한 출력을 쓰고, 그 외에는 예상 출력으로 표시한다. 경로·PID·버전처럼 달라지는 값은 예시 값임을 적는다. 화면 전환이나 출력 없는 명령은 프롬프트 변화 또는 확인 명령과 그 출력을 보여 준다.
- 예를 들어 리다이렉션에서는 `printf 'INFO 시작\n' > app.log`와 `printf 'ERROR 실패\n' >> app.log`를 순서대로 실행한 뒤 `cat app.log`로 두 줄이 남는 것을 보여 준다. 이어서 두 번째 명령에 `>`를 쓰면 마지막 줄만 남는 이유를 설명한다. 파이프에서는 앞 명령의 출력 중 어떤 내용이 다음 명령의 입력이 되는지 짚는다.

### 2. 어려울 수 있는 점

- 혼동하기 쉬운 개념이나 실습 오류를 짧게 적고, 증상과 바로 확인할 지점을 한 쌍으로 제시한다.

### 3. 헷갈린 부분

- 대화에서 사용자가 실제로 헷갈린 부분만 기록한다. 어떻게 이해했는지와 바로잡은 내용이 확인되면 함께 적는다. 해당하는 내용이 없으면 `없음`이라고 쓴다.

### 4. 이 배운 내용으로 할 수 있는 것

- 회사 업무 상황과 사용할 명령·개념, 확인할 결과를 연결한다. 예를 들어 `서비스 로그에서 grep -n으로 오류 줄 번호를 찾고, tail로 최근 기록을 확인한다`처럼 적는다.
